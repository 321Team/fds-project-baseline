## 4. I01 — 코드·실제 관측·권고의 분리

### 확인한 동작

[API](https://github.com/321Team/fds-msa/blob/6531b51c991535794c1f9705dc14f199001d1961/transaction-api/app/main.py)는 문자열을 `datetime.fromisoformat`으로 파싱하고 offset을 붙이거나 UTC로 정규화하지 않은 채 전달/저장한다. 누락하면 aware UTC 서버 시각을 쓴다. [R04](https://github.com/321Team/fds-msa/blob/6531b51c991535794c1f9705dc14f199001d1961/fds-engine/app/rules.py)는 naive를 UTC로 간주한 뒤 KST로 변환한다. [DB 쿼리 표현](https://github.com/321Team/fds-msa/blob/6531b51c991535794c1f9705dc14f199001d1961/transaction-api/app/db.py)은 timezone=True다.

Python3.12.14에서 API의 실제 시간 파싱 AST 식과 R04 소스를 로컬 실행했다. HTTP·DB·서버 호출0이다. [결과 JSON](I01_OFFLINE_RESULT.json)의 9사례는 **OFFLINE_SOURCE_CHARACTERIZATION**이며 기존 Runtime224와 분리한다.

| 입력(금액150만원) | 엔진의 KST 해석 | R04 |
|---|---|---|
| `2026-10-14T02:30:00` | `2026-10-14 11:30+09` | false |
| `2026-10-14T02:30:00+09:00` | `2026-10-14 02:30+09` | true |
| `2026-10-13T17:30:00Z` | 위와 같은 시각 | true |
| `00:59:59+09` / `01:00:00+09` | 경계 전/시작 | false / true |
| `04:59:59+09` / `05:00:00+09` | 경계 직전/종료 | true / false |

224의 실제 I01도 naive02:30→API201·detected=false·skipped=false, DB `11:30+09`로 관측됐다. DB 값은 해당 회차 실측이며 오프라인 Python 결과로 DB 저장을 재검증한 것이 아니다. 이를 “DB가 임의로9시간을 더하는 버그”라고 단정하지 않는다.

**관련 영향:** [context.py](https://github.com/321Team/fds-msa/blob/6531b51c991535794c1f9705dc14f199001d1961/transaction-api/app/context.py)는 R01/R07 이력을 서버 now 기준 하한 `occurred_at >= now-window`만으로 조회한다. 상한이 없어 미래 occurred_at도 조건에 포함될 수 있다. 예를 들어10:25 KST 수신 시 naive02:30가11:30 KST로 저장된 회차는, 같은 계정의 후속 거래에서 이력 집계 영향을 줄 가능성이 있다. 이번에는 술어를 로컬 확인했으며 실제 후속 DB 집계/오탐을 재현하지 않았다. I01을 R04 표시 문제만으로 축소하지 않는다.

또한 잘못된 시간 문자열은 API의 DB 예외 처리 이전 파싱에서 ValueError를 낸다. 오프라인 파싱 오류는 확인했지만 실제 HTTP 응답은 시험하지 않았다. 이를 새 Runtime500 관측으로 기록하지 않는다.

### APP Lead에게 제출할 입력 규약 후보

> 거래 클라이언트는 occurred_at을 UTC 기준 ISO8601 `Z`로 보낸다. 예: KST 2026-10-14 02:30은 `2026-10-13T17:30:00Z`다. 기존 명시적 offset 입력(`+09:00`)은 현재 구현·회귀 결과에서 같은 시각으로 처리되며 그 사실을 유지한다. 시간대 없는 값은 KST로 해석되지 않을 수 있으므로 신규 클라이언트 입력에서 사용하지 않는다. 발생시각과 서버 수신시각은 별도이며 R04는 KST 01:00 이상05:00 미만을 판정한다. 과거 입력·DB 자료는 자동 수정하지 않는다.

권고 이유: 기존 내부 계약의 UTC 표기와 현재 R04 계산·실측에 부합하며 서버 변경 없이 입력 모호성을 줄인다. 이 문구는 **제안**이다. 기존 API가 naive를 거부한다거나 팀이 이미 새 계약을 승인했다고 표시하지 않는다. 오프라인 결과만으로 I01 INFO를 PASS 또는 수용 완료로 승격하지 않는다.

다음 경우에는 문구만으로 닫지 않는다: 실제 클라이언트가 계속 naive를 보내는 경우, naive=KST가 승인 계약이라는 근거가 있는 경우, 신뢰할 수 없는 발생시각의 R01/R07 영향이 허용되지 않는 경우. 이때 별도 API 검증/정규화 또는 이력 상한 변경안을 작성하고 정상 offset·누락/오류·R04경계·R01/R07·DB회귀를 검증한다. 새 정책·허용 오차·기존 데이터 변환값은 임의로 확정하지 않는다.
