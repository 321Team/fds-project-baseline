# 코드 병합 독립 리뷰와 Lead 위임 정책

결정일: 2026-09-18 KST. 근거: 프로젝트 사용자 이권욱의 지시 — “코드 병합 절차만 독립 리뷰절차를 거치고 그 외 절차는 리드에게 일임”.

이 문서는 위 사용자 결정을 저장소에 기록하는 운영 정책 변경이다. 문서 PR의 병합·정본 패키지 발행 상태는 실제 GitHub 기록으로 구분한다. 정책 변경만으로 기존 티켓, Runtime 또는 Release가 완료되지는 않는다.

## 1. 적용 원칙

- **독립 리뷰는 코드 변경을 병합할 때만 필수다.** 코드 외 절차의 검토·실행 여부·결과 수용·인수·종결은 해당 업무의 Lead가 결정한다.
- Lead는 기존 책임 티켓/Decision/CR의 Lead다. 전체 업무를 한 명에게 재배정하거나 Support에게 새 승인권을 부여하지 않는다. 문서 정본과 Release는 정본 발행 담당 Lead가 결정한다.
- Support는 필요한 기술 지원·보안 및 타 영역 영향 확인에 참여한다. 코드 병합 외 단계에서 Support의 별도 서명·승인 대기를 일률적 필수 조건으로 두지 않는다.
- 기존 Baseline §3.4·§17, Release/Ticket 정책, 개별 Runbook의 일반적인 “Support Review/독립 승인 후 실행·Done” 문구와 충돌하면 사람 간 승인 절차에 한해 이 정책을 우선한다. AC, 시험, 선행조건, 증적, 보안 통제는 유지한다.
- 과거 승인·리뷰·발행 이력과 불변 Tag/배포 묶음은 보존한다. 차기 정본에는 이 변경결정과 적용 범위를 동기화한다.

## 2. 코드와 문서의 구분

| 구분 | 예시 | 병합 판단 |
|---|---|---|
| 코드 변경 | 애플리케이션, 테스트, 스크립트, IaC/Ansible, Kubernetes manifest, CI/CD workflow, 의존성/lock, 인증서 profile, 실행 시 소비되는 정책·설정 | 작성자 외 적격 검토자 최소 1인의 독립 리뷰 후 Lead가 병합 결정 |
| 문서·증적만 변경 | 설명/계획/정책/Runbook, WBS, Release 기록, 원본 로그·hash·공개 지문 등 실행 입력이 아닌 기록 | Lead 검토 후 병합 가능. 작성자와 Lead가 같아도 별도 독립 승인 불필요 |
| 혼합 변경 | 문서와 코드가 함께 포함된 PR | 코드 변경 기준 적용 |

확장자나 PR 제목으로 분류하지 않고 실제 사용처와 diff를 확인한다. Markdown에 넣은 새 실행 로직을 실제 배포 입력으로 사용하는 경우, 자동화가 소비하는 JSON/YAML·Trust bundle·설정값, 실행형 웹 코드 변경은 코드 변경이다. 기존 명령의 설명이나 실행 결과 기록만 바뀌면 문서 변경이다. 운영 작업이라는 이름으로 미검토 코드 변경을 우회 적용하지 않는다.

## 3. 코드 병합 절차

1. 작성자는 책임 티켓/AC, 변경·영향·복구, 검증 결과·제한, 대상 HEAD를 PR에 기록한다.
2. 작성자 외 적격 검토자 1인 이상이 실제 diff와 관련 검증을 확인한다. 기존 역할 범위 내 대체 Reviewer를 사용할 수 있다. 작성자 자신의 검토와 AI 보조 점검은 타인의 독립 승인이 아니다.
3. Lead는 최신 HEAD, 독립 검토 근거, 해당 단계의 필수 검사 및 미해결 차단사항을 확인해 병합한다. 새 commit은 변경 부분과 영향 범위만 다시 검토하며 무관한 시험은 반복하지 않는다.
4. GitHub APPROVED, 기술 검토 의견, Reviewer 지정, 실제 Merge를 구분한다. 보호 기능이 제한돼도 정확한 SHA의 독립 검토 기록과 Lead의 수동 병합 판단을 보상 통제로 남긴다.

작업 브랜치·PR·수동 병합과 직접 main push 금지 원칙을 유지한다. CODEOWNERS에 이름이 있다는 사실만으로 독립 승인 완료를 주장하지 않는다. 문서 전용 PR은 Lead 결정 기록을 사용하며 작성자 자신의 GitHub APPROVE를 요구하지 않는다.

## 4. Lead가 결정하는 절차

| 절차 | Lead의 판단과 남길 근거 |
|---|---|
| 문서·계획·Decision/CR·정본 후보 검토 | 해당 책임 범위의 결정, 변경 이유·영향, 관련 기록 및 필요 정합성 검증 |
| 운영 Runtime 실행, 배포, 영구 반영, 복구 | 검토·병합된 코드/설정의 SHA·Digest, 대상·선행조건·성공/중단 기준·복구 방법, 실제 결과 |
| CA 발급·갱신·회수·Trust 적용 | 기존 CA/서비스 담당 범위, 승인 profile·자산·유효성·공개 지문, 실행/검증 결과. 개인키·Secret 비저장 유지 |
| 증적 수용, AC 인수, Gate/Milestone 및 티켓 종결 | 필수 AC와 실제 원본 증적, 미실행·제한·잔여 작업, 해당 단계 판정 |
| 정본 최종화·Release 발행 | 문서 Lead 판단, 버전/Manifest/해시/필수 배포물 검증, 실제 병합·Tag·발행 결과 |

병합 전 정적 검사·단위/모의 시험·CI 및 필요한 격리 환경 시험은 후보 SHA와 시험 범위·격리/복구 조건을 기록하고 Lead 판단으로 수행할 수 있다. 이를 위해 코드 병합이나 독립 승인을 먼저 받도록 요구하지 않는다. 후보 시험 결과를 운영 배포·영구 반영 완료로 표시하지 않는다.

Lead가 직접 수행한 업무도 위임 범위 안에서 결과를 검토하고 인수할 수 있다. 동일 코드의 Runtime 실행·증적 수용·Done마다 독립 Reviewer를 다시 기다리지 않는다. 단, 새 코드/실행 설정 변경이 필요하면 §3으로 돌아간다.

여러 단계의 판단은 한 티켓/PR의 한 기록에 함께 남길 수 있다. 단계별 결과만 구분하며 승인 문서나 PR을 단계마다 추가 생성할 필요는 없다. 다른 업무 영역의 산출물은 해당 Lead의 수신 조건과 연결하고, Support 협의를 새로운 상시 이중 승인 절차로 만들지 않는다.

## 5. 유지하는 통제와 기록

- AC·아키텍처·보안 기준의 실질적 변경은 해당 범위 Lead가 Decision/CR에 변경 이유·영향을 기록하고 정본에 인계한다. 단순 검사 실패를 승인 절차 간소화로 PASS 또는 AC 충족으로 바꾸지 않는다.
- STATIC / MOCK / CI / RUNTIME / REVIEW / MERGE / PUBLICATION은 별도 상태다. 코드 병합은 Runtime PASS가 아니며 CI 0건은 NOT RUN이다. SHA-256 일치는 무결성 확인이다.
- Lead 결정은 기존 기록에 `대상/단계 · Lead · KST 시각 · SHA/Digest(해당 시) · 검증/증적 · 판정/잔여 · 복구(해당 시)`를 남기면 된다. 적용되지 않는 항목의 별도 서류를 요구하지 않는다.
- GitHub 계정·조직/저장소 권한·Ruleset·Actions/Runner 접근은 이 문서로 변경되지 않는다. 정책 채택을 개별 서버 작업·배포·키 발급의 실제 수행 승인이나 완료로 기록하지 않는다.
- 본 변경 시점에 진행 중인 코드/혼합 PR은 독립 코드 리뷰를 유지한다. 문서만 포함된 PR과 코드 외 업무는 Lead 위임 기준을 적용한다. 과거의 승인자를 새 판정의 승인자로 복제하지 않는다.
