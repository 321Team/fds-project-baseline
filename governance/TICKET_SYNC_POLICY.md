# Ticket Synchronization Policy

Version: 1.3 · 2026-09-25 · §5.1 Issue 본문 쓰기와 AI 도구를 추가했다. AI 도구의 본문 직접 수정은 금지하고, 필수 속성·잔여 항목 갱신은 줄 단위 치환과 재조회 대조를 조건으로 허용한다(본문 손상 재발 방지, 사용자 지시) 2026-09-26: Milestone 설명에서도 같은 footer 추가가 확인되어, 적용 범위를 Milestone 설명 등 GitHub 텍스트 필드로 넓히고 텍스트를 보내지 않는 메타데이터 변경의 조건을 추가했다(5)·6)). 이전: 1.2 · 2026-09-18 · 사용자 결정에 따른 승인 절차 개정. [Lead 위임 정책](REVIEW_AUTHORITY_POLICY.md)에 따라 코드 병합과 `fds-project-evidence`의 PR은 독립 리뷰하며, 그 외 문서·실행·업무 결과 수용·종결은 해당 Lead가 결정한다. 운영 속성 보정과 정본 발행 상태는 구분한다.

## 1. 필드별 권위와 충돌

| 대상 | 권위 | 충돌 처리 |
|---|---|---|
| Record ID, 계획, Scope, 책임, 일정 | RELEASED 문서와 승인된 변경 기록 | 최신 날짜라는 이유만으로 덮어쓰지 않음 |
| 실제 실행, 리뷰, 완료일 | 해당 티켓의 실제 증적·승인·종결 이력 | 오래된 Ticket Pack 상태로 되돌리지 않음 |
| Label, Assignee, Issue Type, Milestone | 확인된 속성의 운영 표현 | 본문과 대조하고 불일치는 HOLD |
| 다음 정본 반영 | 후보 PR 및 RELEASE_POLICY | 이슈 동기화를 정본 발행으로 확대하지 않음 |
| Notion | 승인된 입력본 및 원격 반영 결과 | GitHub 갱신만으로 동기화 완료라고 하지 않음 |

Issue 본문 상단 17개 속성표만 메타데이터 입력으로 읽는다. 아래 `보관 입력본`은 역사적 기록이다. 본문 전체를 대충 검색하여 과거 상태를 현행 값으로 선택하지 않는다. 실행 상태 변경 근거는 해당 기록에 연결되어야 한다. 각 실행의 변경 범위는 그 실행 계획과 전후 증적으로 확인한다.

필수 속성: Record ID, Phase, Category, Type, Status, Priority, Start, End, Calendar Days, Working Days, Lead, Support, Exit Criteria, Related Decision IDs, Related Risk IDs, Source, Schedule Note.

## 2. 유일키와 Upsert

1. open/closed와 전체 페이지를 조회하고 PR을 제외한다.
2. Record ID가 없거나 중복, 제목 접두어/기존 migration marker와 불일치하면 Apply를 중단한다.
3. 알려진 Record ID를 기존 Issue에 Update한다. 이 스크립트는 새 Issue를 만들지 않는다.
4. `<!-- fds-notion-migration:... record-id:... -->`는 과거 이관 이력이다. 날짜 변경이나 재생성 없이 보존한다.
5. 대상 목록·본문 SHA-256·상태·기존 메타데이터를 계획에 고정하고 실제 반영 직전에 다시 대조한다.
6. 수동 변경/댓글 갱신 등으로 스냅샷이 달라지면 새 계획을 만든다. 반복 실행은 차이 없는 항목을 쓰지 않는다.

## 3. 상태와 종결

| 본문 Status | GitHub state | state_reason | Label |
|---|---|---|---|
| To Do | open | 해당 없음 | status:to-do |
| In Progress | open | 해당 없음 | status:in-progress |
| In Review | open | 해당 없음 | status:in-review |
| Blocked | open | 해당 없음 | status:blocked |
| Done | closed | completed | status:done |
| Cancelled | closed | not_planned | status:cancelled |

Blocked는 업무 진행 상태이며 Runtime Gate HOLD와 같은 값이 아니다. Gate HOLD만으로 Status를 자동 변경하지 않는다. 기존 티켓에 없는 확장값은 허용 사전일 뿐 상태 변경 지시가 아니다.

담당 Lead는 필수 AC·원본 증적·잔여 작업을 확인해 자기 업무의 인수·종결을 결정한다. 코드 병합 외 단계의 Support 독립 승인을 반복 필수화하지 않되, `fds-project-evidence`의 편입·정정 PR은 독립 리뷰를 유지한다. 이 위임은 아래 동기화 스크립트의 자동 쓰기 범위를 확대하지 않는다.

동기화 스크립트는 state/state_reason을 쓰지 않는다. 불일치하면 근거와 담당자 판단을 요청한다. Done 티켓도 모든 AC를 자동 체크하지 않는다. 결정 완료·미도입/유예·N/A·이관·Runtime NOT RUN을 구분한다. 예를 들어 #4~6 Done은 미도입/유예 결정 종결이지 신규 기능 구현 PASS가 아니다. 기존 승인자·Reviewer를 새 승인으로 복제하지 않는다.

## 4. 속성 예외

- `원본 속성 미확인`: 해당 필드는 추정하여 쓰지 않는다. #59 D-ARC-01·#61 D-WBS-01은 2026-09-11 첨부 원본으로 속성 복원이 완료됐다. 날짜·기간 모순은 같은 날 사용자 정정(#59 End 8/26, #61 Completed Date 8/26)으로 해소됐고 차기 정본 반영은 별도 잔여이며, 과거 미확인 표시는 이력으로 보존한다.
- 필드 존재와 값 확정을 구분한다. `TBD`인 승인 일정은 누락 값으로 임의 대체하지 않는다.
- Start/End는 유연하게 조정 가능한 계획 목표이며 Completed Date와 구분한다. 날짜 변경 자체를 승인 차단이나 Runtime FAIL로 판정하지 않는다. 계획 변경 시 현행 문서와 티켓의 값·근거를 정합화하고 실제 완료일·기간은 원본 증적 없이 바꾸지 않는다.
- Category의 전체 의미는 본문에 보존하고 기존 대표 `area:*`만 유지한다. 임의 다중 라벨 대량 추가 없음.
- 단일 Milestone 매핑 미확정은 null을 확정 N/A로 해석하지 않는다. `HOLD`로 기록한다.
- 존재하지 않는 Label/Type/Milestone을 즉석 생성하지 않는다. 카탈로그 계획과 별도 명시적 적용으로 관리한다.

## 5. 안전한 쓰기와 감사

- 허용 쓰기: 확정된 labels, assignees, 기존 카탈로그의 정확한 native type/milestone.
- 금지 쓰기: body/title/Record ID/AC/Source/일정/승인/종결, 댓글 삭제, close/reopen, 권한·Ruleset 변경, main push/merge/발행.
- 사용자 수동 라벨과 추가 Assignee를 보존한다. 같은 관리 namespace의 충돌 라벨은 자동 삭제하지 않고 중단한다.
- 인증/권한 실패, 403/404/409/422, stale plan 또는 응답 불일치가 발생하면 중단한다. 연결 토큰 추출·권한 우회·다른 계정 전환은 하지 않는다.
- 적용 건마다 before → 요청 필드 → 재조회 결과를 기록한다. 실패 시 이후 건을 멈추고 부분 완료를 보고한다. 자동 롤백으로 동시 편집을 덮어쓰지 않는다.
- 원본 본문·메타데이터 스냅샷은 보안 통제된 별도 감사 경로에 보관한다. 토큰·Secret·개인키를 기록하지 않는다.

### 5.1 Issue 본문 쓰기와 AI 도구 (수동 편집 포함)

§5는 동기화 스크립트의 자동 쓰기를 다룬다. 이 절은 자동·수동을 가리지 않고 Issue 본문(body) 쓰기에 적용한다.

**AI 도구의 범위.** 이 프로젝트에서 쓰는 모든 AI 도구가 대상이다. Claude(Claude Code), GPT(ChatGPT·Codex), Grok, Cursor 등이 여기에 포함된다. 쓰기 경로도 가리지 않는다. GitHub MCP·커넥터, 도구가 대신 실행하는 `gh`/API, 에이전트 모드의 브라우저 조작이 모두 대상이다.

**배경.** 2026-09-22~24에 Claude 세션 경로로 쓴 본문에서 손상이 반복 관찰됐다.
- 손상 유형: `<`·`>`의 HTML 엔티티화, 링크 앞뒤 ``` `` ``` 삽입, 둥근 따옴표 변환, footer 추가
- 수정 대상이 아닌 줄까지 바뀌었다. #74·#75는 속성표 Start/End 값만 갱신한 편집에서 손상됐다.
- 다른 도구에서는 손상이 관찰되지 않았다. 손상 조건은 확인하지 못했다.
- 근거: [복구 기록](../audit/phase2-repo-bootstrap-20260923/issue-body-repair-20260925/README.md) §2·§2-1

#### 1) 금지 — 본문 직접 수정

AI 도구는 아래 편집을 하지 않는다.
- 본문 전체 재작성
- 절·문단·표의 추가·삭제·수정
- 링크·관리 마커(`<!-- … -->`)·보관 원문 편집
- 그 밖에 2)에 해당하지 않는 모든 본문 변경

이런 변경은 3)의 절차로 담당자가 반영한다.

#### 2) 허용 — 필수 속성과 잔여 항목 갱신

AI 도구는 다음 항목을 갱신할 수 있다.
- 본문 상단 필수 속성표(§1의 17개 속성)의 값
- AC·Exit Criteria 등 체크리스트의 체크 상태(`[ ]`↔`[x]`)
- 잔여 항목 표기

갱신할 때는 아래 조건을 모두 지킨다.

1. **해당 줄만 바꾼다.** 조회한 원문에서 대상 줄의 값·체크 표시만 문자열로 치환해 올린다. 모델이 본문 전체를 다시 출력해 쓰지 않는다. 다른 줄은 바이트 그대로 둔다.
2. **쓰기 직전에 `updated_at`을 다시 확인한다.** 조회 뒤 다른 편집이 있었으면 다시 조회해서 새로 만든다.
3. **쓰기 뒤에 재조회해 대조한다.** 확인할 것은 두 가지다.
   - 바뀐 줄 외 차이가 0이다.
   - 손상 신호(`&lt;`·`&gt;`·단독 ``` `` ```·footer)가 늘지 않았다.

   하나라도 어긋나면 추가 쓰기를 멈추고 코멘트로 보고한다. 담당자는 편집 이력(`userContentEdits`)으로 직전 revision을 확보해 복구한다.
4. **근거를 코멘트로 남긴다.** 바꾼 항목, 전→후 값, 근거(결정·증적 링크), AI 사용 표기(예: `AI 사용: CODEX_ASSISTED`)를 적는다.
5. **재조회 대조를 할 수 없는 도구는 이 허용을 쓰지 않는다.** 예를 들어 파일·셸 접근이 없는 웹 채팅이 해당한다. 이런 도구는 변경안을 코멘트로 남긴다.

판단 권한은 바뀌지 않는다.
- Status, AC 충족·인수, 종결은 담당 Lead가 결정한다([REVIEW_AUTHORITY_POLICY §4](REVIEW_AUTHORITY_POLICY.md)).
- 일정은 승인된 변경 기록을 따른다(§1, §4 속성 예외).
- AI 도구는 그 결정과 근거를 반영할 뿐이며, 스스로 충족을 판정하지 않는다.
- Status를 바꾸면 §3 표의 state·label과 맞춘다.

§5의 금지 쓰기는 동기화 스크립트의 자동 일괄 쓰기에 계속 적용된다. 2)는 개별 Issue에 대해 사람이 지시한 갱신에만 적용한다.

#### 3) 그 밖의 본문 변경 — 담당자가 반영

1. 교체 본문 파일(UTF-8, LF)과 plan을 준비한다. plan에는 `number`, 직전 재조회 `updated_at`, 변경 전 본문 SHA-256(LF), 파일 SHA-256을 적는다. AI 도구가 준비해도 된다.
2. 점검 실행으로 파일 해시와 계획 이후 수정 여부를 확인한다.
3. 반영한다. 반영은 담당자가 로컬 `gh`로 직접 실행하고, AI 도구에 맡기지 않는다.
4. 읽기 전용으로 재조회해 본문 바이트 일치, 보관 원문 해시, 제목·상태·라벨 불변을 확인한다.

기준 스크립트는 [`apply-evidence-path.ps1`](../audit/phase2-repo-bootstrap-20260923/evidence-path-batch/apply-evidence-path.ps1)이다. 짧은 수정은 사람이 GitHub 웹 UI에서 직접 편집해도 된다. 웹 UI는 본문 65,536자 한도가 있다.

#### 5) Milestone 설명 등 그 밖의 GitHub 텍스트 필드

- **적용 대상:** 1)~3)은 Issue 본문 외에 Milestone 설명(description)에도 똑같이 적용한다. 2026-09-26 세션 경로로 Milestone #5 설명을 갱신하자 요청한 적 없는 footer(`_Generated by [Claude Code](…)_`)가 끝에 붙었다. 보낸 설명 텍스트는 바이트 그대로였는데도 그랬다. 근거: [Milestone 기한 정정 기록](../audit/milestone-due-fix-20260926/README.md).
- **같은 판단 기준:** 이 밖에 재조회 대조 없이 쓰는 긴 설명 텍스트(Release 설명 등)도 같은 기준으로 판단한다.
- **예외:** 코멘트와 PR 본문은 이 절의 금지 대상이 아니다. footer가 붙을 수 있다는 점만 감안한다.
- **Milestone 설명 변경:** 사람이 웹 UI에서 직접 편집한다. AI 도구는 바꿀 문구만 준비한다.

#### 6) 텍스트를 보내지 않는 메타데이터 변경

Milestone 기한(`due_on`), Issue 날짜 필드(Start date·Target date) 같은 값만 보내는 변경은 AI 도구가 할 수 있다. 조건은 다음과 같다.

1. **요청에 텍스트 필드를 넣지 않는다.** 설명·본문을 함께 보내면 5)의 금지 대상이다.
2. **쓰기 직전에 대상의 `updated_at`과 현재 값을 다시 확인한다.** 계획 이후 변경이 있으면 멈춘다.
3. **쓰기 뒤에 재조회해 대조한다.** 확인 항목은 두 가지다.
   - 바꾼 값이 계획과 같다.
   - 제목·상태·설명 등 다른 필드가 바이트 그대로다.

   어긋나면 멈추고 보고한다.
4. **변경 전 상태, 요청 값, 재조회 결과를 기록한다.**
5. **판단 권한은 그대로다.** 일정 값은 승인된 변경 기록(§1, §4)에 근거가 있어야 한다.

#### 4) 항상 허용

- 읽기 전용 조회와 대조: 필수 속성 누락, AC 잔여 항목, 증적 연결 점검
- 교체 본문 파일과 plan 준비
- Issue 코멘트(AI 사용 표기 포함). Claude 세션 경로의 코멘트에는 footer가 붙을 수 있다.

## 6. 완료 판정

`COMPLETE`: 중복/필수 속성 누락/허용값 오류/계정·상태·메타데이터 불일치가 0이며, 요구된 native Type 및 Milestone이 확인되거나 근거 있는 N/A·대체 승인이 있다.

`PARTIAL`: Label/담당자 일부 완료라도 source unknown, native 기능 미반영, Milestone HOLD가 남음. 전체 PASS로 쓰지 않는다.

`STOP`: 권한 오류, 식별 충돌, 변경 중 drift, 결과 검증 실패. 추가 쓰기를 중단하고 원인·적용 완료 번호·미적용 번호를 보고한다.

## 7. 정본 인계

현재 발행 정본은 [CURRENT.md](../CURRENT.md)와 실제 GitHub Release로 확인하며 후속 검토 후보와 구분한다. 승인된 이번 운영 속성 보정은 다음 후보의 정책·감사 기록에 연결한다. README/정책만 변경한 PR은 정본 Lead가 정확한 SHA를 검토·결정한다. 코드/자동화 변경이 함께 있으면 최소 1인의 독립 코드 리뷰가 필요하다. 기존 Release 묶음 검증은 유지하며 최종화·발행은 정본 Lead가 결정한다. Ticket Pack/WBS/Release의 상태·기간·증적을 이번 메타데이터 작업만으로 재발행하지 않는다.
